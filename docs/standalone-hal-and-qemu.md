# Standalone HAL and QEMU emulation workflow

AyeDrive now separates three evidence layers:

1. **Standalone HAL simulation**: every contracted device family is launched as an independent JSON-lines process and exercised through a common lifecycle/submit/cancel/reset/time contract.
2. **OS binding/emulation**: an OS-specific binding or authorized QEMU guest may execute the standalone test package. The result is recorded per OS target.
3. **Physical and regulated evidence**: physical HIL, EMC/electrical/RF/thermal/clinical testing, independent review, accredited laboratory work, regulator/customer approval, and certification remain separate gates.

## Shared matrix

`DriverTest/models/standalone-hal-os-matrix.json` is the source of truth for the shared HAL contract, five OS targets, QEMU applicability, and all 15 device families. Validate its shape with `standalone-hal-os-matrix.schema.json` using the repository's normal schema tooling.

The shared HAL contract requires:

- ABI version 1;
- start, submit, cancel, reset, stop, and monotonic logical time;
- deterministic invalid-request handling;
- deterministic fault injection and recovery;
- family-specific exercise behavior;
- independent process execution and structured audit output.

## Run standalone HAL evidence

From the repository root:

```powershell
$env:PYTHONPATH = "$(Get-Location);$(Join-Path (Get-Location) 'tools')"
python -m tools.ayeadrive_sim.hal_harness --output artifacts/ayeadrive
```

The output is `artifacts/ayeadrive/ayeadrive-hal-report.json`. A passing report means that the software HAL contract and family exercises passed in the host environment. It does not establish hardware behavior.

## Run the C display simulator

The display simulator uses the same C HAL model for both visible and automated execution:

```bash
make -C Shared display-linux-x11
```

Visible mode is the default. It requires a Linux X11/WSLg display and X11 development headers. For automation, headless mode must be requested explicitly:

```bash
make -C Shared test-display-linux-headless
```

The headless target is not evidence that a display window was shown.

## Run the WebGPU display viewer

From PowerShell on Windows:

```powershell
powershell -ExecutionPolicy Bypass -File tools/run_webgpu_display.ps1
```

Or from Python on any supported host:

```bash
python tools/webgpu_display_server.py
```

The server opens `http://127.0.0.1:8765/index.html`. The server launches `Shared/build/display_web_source`, which calls the C display HAL and exposes its completed framebuffer at `/frame`. The page uses WebGPU when the browser exposes it and falls back to Canvas 2D when WebGPU is unavailable. If the C producer is unavailable, the page shows an error and does not fabricate frames. This browser viewer is a visible display frontend; it is not, by itself, QEMU guest evidence.

## Run QEMU emulation

The QEMU runner is deliberately input-gated. It does not download operating systems, guess checksums, attach host disks, or claim a guest result without authorized media:

```powershell
python tools/ayeadrive_qemu.py `
  --iso C:\path\to\authorized\guest.iso `
  --iso-sha256 <64-hex-expected-sha256> `
  --output artifacts/qemu/ayeadrive-qemu-report.json
```

Without `--iso` and `--iso-sha256`, the runner writes a deterministic `not_run` report and exits successfully so the broader audit can continue while preserving the missing prerequisite. With media supplied, it verifies the checksum. Add `--launch` only when an authorized guest launch is intended; the runner then creates a disposable qcow2 disk, disables networking and passthrough by default, and launches an ephemeral QEMU guest.

A QEMU boot is not itself an OS/device conformance result. A guest-specific runner must install or start the target binding, invoke the standalone HAL/family tests, collect structured output, and identify the guest OS, kernel/build, QEMU version, machine type, acceleration mode, media checksum, and test command.

### QEMU HAL display transport

The display vertical slice uses a QEMU `virtio-serial` port rather than treating QEMU's own window as the simulated device display:

1. Build `make -C Linux display-guest` and place `Linux/build/display_guest` in authorized guest test media.
2. Start the host bridge: `python3 tools/display_x11_bridge.py /tmp/ayeadrive-display.sock`.
3. Launch the authorized guest with `tools/ayeadrive_qemu.py --launch --display-bridge --display-socket /tmp/ayeadrive-display.sock`.
4. Inside the guest, run `/path/to/display_guest`; it calls the C display HAL and writes completed framebuffer frames to `/dev/virtio-ports/ayeadrive.display`.

The Python runner still defaults to `-display none`, `-nic none`, and no display channel. `--display-bridge` is explicit and requires `--display-socket`. The bridge window is host WSLg/X11 output; the pixels are generated by the guest HAL client. This path is not claimed as executed until an authorized guest image boots, the guest client runs, and the host bridge receives frames.

## Architecture boundary: native, QEMU, and guest paths

QEMU is optional. The preferred native host-OS path is `Host OS <-> AyeDrive HAL <-> AyeDrive device simulation`; a compatibility shim may temporarily connect the HAL to an existing QEMU device simulation. When QEMU is explicitly used, the preferred path is `Host OS <-> QEMU <-> AyeDrive HAL <-> AyeDrive device simulation`, with `AyeDrive compatibility shim <-> QEMU device simulation` as the quick fix.

For a guest OS, the host-side QEMU layer and guest-side OS layer are independent. Preferred operation uses an AyeDrive device simulation at both layers; mixed combinations may use the compatibility shim on either side. Unmodified QEMU is also supported, with its normal limitations, while the guest may still use the preferred AyeDrive simulation directly. These are separate from the existing native Windows, Linux, Android, macOS, FreeRTOS, and Arduino adapters.

The compatibility shim is AyeDrive-owned and is not an in-OS display client. `Linux/user/display_guest.c` remains a separate test artifact and is not the QEMU device path.

### Strict QEMU source policy

This repository never carries QEMU source, vendored QEMU code, or adapted QEMU files. QEMU device-use build scripts and Makefiles may obtain source only through the host OS package source mechanism or the official QEMU upstream repository. They must pin and validate the QEMU version, build and test against the external checkout, and keep the checkout/build output outside repository content. Only AyeDrive-owned adapter contracts, scripts, tests, and provenance records are released.

## OS status boundaries

- Windows UMDF: the repository has a Windows interface smoke path and an existing Windows QEMU launcher; target-driver behavior requires a licensed Windows guest and signed package.
- Linux: the repository has a protocol/reference binding; kernel module evidence requires matching headers and a disposable Linux guest.
- Android: the repository has an AIDL starter; Android SDK/AOSP/BSP, service, SELinux, and guest/device evidence are separate prerequisites.
- macOS: DriverKit cannot be completed by QEMU on this host; native macOS/Xcode/entitlement validation remains required.
- FreeRTOS: a QEMU board model and toolchain must be selected; generic x86 QEMU is not evidence for a particular MCU/BSP.

All QEMU results must retain `certification: not_claimed` and `physical_hil: not_claimed`.
